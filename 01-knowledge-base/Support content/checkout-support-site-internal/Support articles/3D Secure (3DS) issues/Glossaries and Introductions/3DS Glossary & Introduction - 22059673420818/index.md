## Key Terms & Definitions

| **Term** | **Definition** |
| --- | --- |
| **3DS** | 3D Secure |
| **CKO** | Checkout.com |
| **PSD2** | Payments Services Directive 2 |
| **SCA** | Strong Customer Authentication |
| **3RI ** | 3-D Secure transaction initiated by the 3DS Requestor for the purposes of confirming that an account is still valid or for Cardholder authentication. The first main use case being recurrent transactions (TV subscriptions, utility bill payments, etc.) where the merchant wants to perform a payment transaction to receive authentication data for each bill or a non-payment transaction to verify that a subscription user still has a valid form of payment. The second main use case is when the 3DS Requestor requests Decoupled Authentication as a method to authenticate the Cardholder. |
| **ACS** | The ACS is operated by the issuer, ACS provider, or the issuer’s processor. In response to a Directory Server inquiries, the ACS verifies that the individual card account number is eligible for authentication, receives authentication requests from merchants, authenticates the cardholder during online purchases, and provides digitally-signed authentication response messages (containing the authentication results and other secure data) to the 3DS Server and to the Directory Server. Held in the issuer's domain, this is what the cardholder will authenticate themselves to during a 3D secure transaction. It provides the result to the MPI of whether or not the 3D secure authentication was successful. |
| **AREQ** | The AReq message is the initial message in the 3-D Secure authentication flow. The 3DS Server forms the AReq message when requesting authentication of the Cardholder. It can contain Cardholder, payment, and Device information for the transaction. There is only one AReq message per authentication. |
| **ARES** | The ARes message is the Issuer’s ACS response to the AReq message. It can indicate that the Cardholder has been authenticated, or that further Cardholder interaction is required to complete the authentication. There is only one ARes message per transaction. |
| **AttemptN3D** | A feature that caters for scenarios when a 3D secure charge is attempted, but cannot be completed due to a system malfunction or because the card is not enrolled/enabled for 3D secure. If that happens and the merchant has this feature enabled, the charge will be downgraded to a non-3D secure charge to allow the processing to continue. |
| **CAVV (Cardholder Authentication Verification Value)** | Value generated by the ACS that is signed by the issuer and returned to the merchant in the PARes message. |
| **Challenge Request Message** **(CREQ)** | The CReq message initiates Cardholder interaction in a Challenge Flow and can be used to carry authentication data from the Cardholder. |
| **Challenge Response Message** **(CRES)** | The CRes message is the ACS response to the CReq message. It can indicate the result of the Cardholder authentication or, in the case of an App-based model, also signal that further Cardholder interaction is required to complete the authentication. |
| **DAF (Digital Authentication Framework)** | The framework that aims to provide a consistent and verifiable set of transaction data that can increase confidence and facilitate risk decisions that lead to increased approval rates and lower fraud.. Qualifying transactions that meet the framework criteria will receive fraud liability protection for merchants, as dispute rights for Dispute Condition 10.4: Other Fraud—Card-Absent Environment transactions will be removed. The program outlines a common set of rules and processing standards to ensure consistency in evaluating and managing eligible transactions. The DAF aims to achieve the following objectives: • Improve the performance of card-not-present (CNP) transactions to nearer that of card-present chip transactions • Establish clear criteria for transactions to qualify for merchant fraud liability protection through multiple solutions • Define performance requirements for issuers, acquirers, token requestors and merchants to ensure solutions are deployed in an effective manner, resulting in a positive cardholder experience • Develop a structure that works globally while acknowledging regional differences. |
| **Decoupled Authentication** | Decoupled Authentication is an authentication method whereby authentication can occur independently from the cardholder’s experience with the 3DS Requestor. The authentication method used for Decoupled Authentication is outside the scope of this specification, however one method could be a push notification to a banking app that completes authentication and then sends the results to the ACS. Decoupled Authentication is applicable to all Device Channels. |
| **Delegated Authentication** | Delegated Authentication allows PSPs to delegate the authentication process to eligible third parties. The program allows delegates, such as merchants who are best-in-class for fraud management or token requestors, to continue to define a consistent consumer payment experience when SCA is required while maintaining relevant security controls. Delegated Authentication allows delegates to use either 3-D Secure (3DS) or Token Service (TS) to establish an authentication code needed for dynamic linking, together with indicators for identification factors used as part of delegated authentication. To help establish SCA factors, Token Service also supports merchants using tokens to bind those tokens to customer accounts and devices. Device binding enables the device to be used as a possession factor for SCA within the delegated authentication framework. |
| **DPAN (Device Primary Account Number)** | Device Primary Account Number also known as the "Digital" Primary Account Number) means the "network token" generated by the Payment Network or [issuing bank] that identifies the Provisioned Card that is associated with a Cardholder’s FPAN and used by [issuing bank] to identify the same Card and Account on which to Charge purchase transactions or other transactions using an Enabled Device. |
| **DS (Directory Server)** | A server component operated in the Interoperability Domain; it performs a number of functions that include: authenticating the 3DS Server, routing messages between the 3DS Server and the ACS, and validating the 3DS Server, the 3DS SDK, and the 3DS Requestor. Directory Server is a Scheme Network component in the 3DS2 flow. |
| **Electronic Commerce Indicator** | Payment System-specific value provided by the ACS to indicate the results of the attempt to authenticate the Cardholder. In 3DS1 - Flag included in the PARes message that indicates the level of security used when the cardholder provided payment information to the merchant.   In 3DS2 - value included in the RReq. |
| **EMVCo** | EMVCo facilitates worldwide interoperability and acceptance of secure payment transactions. Supported by dozens of banks, merchants, processors, vendors and other industry stakeholders, EMVCo manages and evolves the EMV® Specifications and related testing processes. This includes, but is not limited to, card and terminal evaluation, security evaluation, and management of interoperability issues. |
| **FPAN (Funding Primary Account Number)** | Funding Primary Account Number means the number of the actual Account appearing on the physical Card (or similar device) issued by [issuing bank]. |
| **MCC (Merchant Category Code)** | The Merchant Category Code (MCC) is a four-digit number assigned to describe a merchant’s primary business. Some MCCs identify a specific merchant or type of transaction (e.g. MCC 7995 Gambling). The Schemes and issuers use MCC data for a range of purposes, including activity tracking, reporting, and risk management. Acquirers (and their agents) are required to assign the correct MCC to each of their merchants. |
| **OOB (Out of band)** | A Challenge activity that is completed outside of, but in parallel to, the 3DS flow. The final Challenge Request is not used to carry the data to be checked by the ACS but signals only that the authentication has been completed. |
| **Risk Based Authentication** | Authentication completed via the frictionless flow based on the issuer assessment of the transaction risk. |
| **RREQ** | The RReq message communicates the results of the authentication. The message is sent by the ACS through the DS to the 3DS Server. There is only one RReq message per authentication. The RReq message is present only in an authentication requiring a Cardholder challenge. |
| **RRES** | The RRes message acknowledges receipt of the RReq message. The message is sent by the 3DS Server through the DS to the ACS. There is only one RRes message per authentication. The RRes message is present only in an authentication requiring a Cardholder challenge. |
| **SCP (Secure Corporate Payment)** | The payments are initiated electronically through dedicated payment processes or protocols that are not available to consumers. |
| **Soft Decline** | When a request is declined, subsequent attempts may be successful. |
| **Third Party Acquirer** | An acquirer that is not Checkout. See acquirer. |
| **Zero Dollar Authorisation** | Allows you to verify a cardholder's payment information upon acceptance without actually billing the customer for a charge. This is done through an authorization for an amount of zero. |
