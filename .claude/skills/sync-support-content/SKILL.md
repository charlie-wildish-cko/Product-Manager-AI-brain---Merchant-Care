# Sync Support Content

Pull the latest content from the `cko-web` GitHub org repos that back `01-knowledge-base/Support content/` and `01-knowledge-base/processes/Care Agent SOPs/`, and drop it in place so the local copies stop drifting from what's actually published.

Source-of-truth mapping (full detail in `01-knowledge-base/processes/support-content-sources.md` — read that file first if anything below is unclear or the repo layout has changed):

| Scope | Repo | Path in repo | Local target |
|---|---|---|---|
| `external` | `cko-web/checkout-support-site` | `Support articles/` | `01-knowledge-base/Support content/checkout-support-site-main/Support articles/` |
| `internal` | `cko-web/checkout-support-site-internal` | `Support articles/` | `01-knowledge-base/Support content/checkout-support-site-internal/Support articles/` |
| `tech-docs` | `cko-web/checkout-docs-site` | `docs/NAS/` | `01-knowledge-base/Support content/Tech Docs/` |
| `api-reference` | `cko-web/checkout-api-reference` | `nas_spec/` | `01-knowledge-base/Support content/API reference/` |

All four sync from `staging` branch (not `main` — `main` has branch protection and nothing deploys from it; `staging` is what's actually live).

Default to `all` if the user doesn't specify a scope.

---

## Step 1 — Pull each requested repo via tarball

`git clone` over HTTPS fails with a 403 — the `cko-web` org enforces SAML SSO on the GitHub CLI OAuth app, and API access works without it. Use the tarball API instead:

```bash
unset GITHUB_TOKEN
mkdir -p /tmp/sync-support-content && cd /tmp/sync-support-content
gh api repos/cko-web/<repo>/tarball/staging > pull.tar.gz
mkdir -p <label> && tar -xzf pull.tar.gz -C <label> --strip-components=1
```

`unset GITHUB_TOKEN` matters — if the env var is set to a stale token, `gh` will use it instead of the working keyring credential and every call 401s. Run this for each repo scope requested (`checkout-support-site`, `checkout-support-site-internal`, `checkout-docs-site`, `checkout-api-reference`).

If `gh api` itself fails (auth, org access, rate limit), stop and report the exact error to the user — don't fall back to guessing content.

## Step 2 — Diff before overwriting

Before replacing anything, compare counts so the user knows what changed:

```bash
# external / internal (article folders contain index.md)
find "<local Support articles path>" -name "index.md" | wc -l
find "/tmp/sync-support-content/<label>/Support articles" -name "index.md" | wc -l

# tech-docs / api-reference: compare file counts under the relevant subfolder instead
find "<local path>" -type f | wc -l
find "/tmp/sync-support-content/<label>/<repo-subpath>" -type f | wc -l
```

## Step 3 — Replace local copies

For `external` and `internal`: replace the `Support articles/` folder wholesale (`rm -rf` the old one, `cp -R` the fresh one in).

For `tech-docs`: replace `01-knowledge-base/Support content/Tech Docs/{Home,Articles,GetStarted}` with the fresh `docs/NAS/{Home,Articles,GetStarted}`.

For `api-reference`: replace `paths/`, `components/`, `future/`, `code_samples/`, `changelog.md`, `README.md` under `01-knowledge-base/Support content/API reference/` with the fresh `nas_spec/` equivalents. **Do not** try to regenerate `api-reference.json` from `swagger.yaml` — the local `.json` is a bundled build artifact (all `$ref`s inlined into one file), not a 1:1 mirror of the raw `swagger.yaml` + `paths/`/`components/` source tree, and there's no build step available here to reproduce it. Leave `api-reference.json` as-is and flag to the user that it's now stale relative to `paths/`/`components/`/`swagger.yaml` if those changed, since it can't be auto-regenerated by this skill.

Always check `git status` on the target files before deleting/overwriting — if there are uncommitted local edits under any of these folders, warn the user and ask whether to proceed, stash, or commit first, rather than silently discarding their work.

## Step 4 — Report and update the "last pulled" date

Report to the user, per scope pulled: old count → new count (added/removed), and anything that looks like a structural change (e.g. new top-level category folder) rather than just new/removed articles.

Update the "Last pulled" line at the bottom of `01-knowledge-base/processes/support-content-sources.md` to today's date and the new counts.

Clean up `/tmp/sync-support-content` when done.
