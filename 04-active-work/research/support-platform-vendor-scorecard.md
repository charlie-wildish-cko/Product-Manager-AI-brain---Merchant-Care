## Structure (revised 2026-09-18)

Categories are organised around seven assessment principles rather than the platform's own feature groupings:

| # | Principle | What it asks |
|---|---|---|
| 1 | Flexible channels, data model and routing | Identify a customer on contact, route cleanly through support channels, no lock-in to a vendor's data model |
| 2 | Integration ease | Integrates well with other systems to receive and pass data (customer records, team transfers, analytics) |
| 3 | AI compatibility | Can embed vendor and custom AI agents for both customers and Ops agents to drive resolution speed, quality, and cost |
| 4 | Agent experience | The interface agents work in, and how they experience routing (queue views, capacity, handoff) — not the routing rules themselves |
| 5 | Config as code | Enhance the stack with AI-assisted code and deploy systematically at velocity |
| 6 | Partnership and reliability | Strategic vendor fit (won't treat us as low-value, won't need heavyweight implementation) plus operational/contractual reliability |
| 7 | Pricing | Won't be a long-term cost burden; provides ROI |

Customer-facing experience is kept as its own, eighth category — it's the external-facing surface, distinct from the internal agent experience in category 4.

**Not scored here**: "Abstract our core services" — the principle that orchestration of customer enrichment/lookup, support channels, AI involvement, and content generation stays under our control, not the vendor's — is an internal engineering design constraint, not a vendor capability. It should inform how categories 2, 3, and 4 are scored (e.g. a vendor's AI or app framework that can't be called from outside should score lower there) rather than appear as its own line.

## How to score

**Step 1 — Requirement scores.** For every requirement in the 8 categories below (each maps one-to-one to a requirement in `support-platform-vendor-requirements.md`), score each vendor 0–3. What 0-3 means depends on what the category actually measures: a technical capability question and a partnership or pricing question aren't the same kind of judgment, even though both share the same 0-3 scale so the weighted math works uniformly across all eight categories.

**Categories 1, 2, 3, 4, 5, 7** (Flexible channels, Integration ease, AI compatibility, Agent experience, Config as code, Customer-facing experience) — architecture and build type:

| Score | Meaning |
|---|---|
| 0 | Not supported — no credible path |
| 1 | Possible via custom build or heavy configuration — meaningful cost, time, or risk |
| 2 | Supported via configuration or paid add-on |
| 3 | Native, out-of-the-box |

**Category 6** (Partnership and reliability) — verification strength and specificity, not build type:

| Score | Meaning |
|---|---|
| 0 | No evidence, or an active negative signal (e.g. a backlog request with no visibility or timeline) |
| 1 | Vendor's own claim only, unverified by us |
| 2 | Verified via reference call or contract, but generic or capped (a target, not a guarantee; a shared CSM queue) |
| 3 | Verified, named, dated, and specific to us (design-partner commitments, a named CSM, a contractual remedy) |

**Category 8** (Pricing) — cost certainty, not capability:

| Score | Meaning |
|---|---|
| 0 | No credible cost model, or cost is a blocker |
| 1 | Modelled estimate only, not vendor-confirmed, real uncertainty |
| 2 | Vendor-confirmed quote or terms, but with a caveat (add-on gating, usage-based variance) |
| 3 | Vendor-confirmed, fully transparent, predictable at our target scale |

A "2" in Partnership doesn't carry the same rigor as a "2" in Integration ease, even though the weighted math treats them identically. That's already true of how this scorecard has been scored in practice, this makes it explicit up front rather than leaving it implicit in each row's evidence text.

**Step 2 — Section score.** A "section" is the smallest scored unit within a category: a named sub-category where one exists (e.g. Agent experience's 4a Interface / 4b Agent-facing routing / 4c Data and permissions), or the category's own flat list of requirement rows where it doesn't have sub-categories. Average the requirement scores within each section — a raw decimal, not rounded to any step (e.g. 1.667, 2.4286).

**Step 3 — Category score.** Base the category score on its section scores: where a category has multiple sections (4, 6), average the section averages. Where it has only one section (1, 2, 3, 5, 7, 8), the category score is that section's average directly. If a vendor has zero evidence in an entire section, leave that section, and the category total that depends on it, blank rather than averaging over the sections that do have data — a partial average would overstate confidence in a category that's mostly unevidenced. No rounding at any level; report to 2 decimal places for readability.

**Step 4 — Weighted total.** Multiply each category score by its weight (below) and sum. Maximum possible total is 3.0. If one or more categories are blank for a vendor, compute a coverage-adjusted total: sum only the available categories' weighted contributions and divide by the sum of their weights, so the result stays on the 0–3 scale, and state the weight-coverage percentage alongside it — never silently present a partial total as if it were complete. Enter results in the Summary table at the end.

Build is out of scope for this scorecard — see RFC Option 4 (not viable at current team capacity).

**Partnership fit** (category 6) is scored the same 0–3 scale but sourced from reference calls and account-team engagement during the RFI/POC period, not a vendor's self-reported answer — treat vendor claims of roadmap commitment or account priority as unverified until a reference customer or named roadmap item confirms it.

### Two scoring axes: Capability vs. Effort

A vendor question surfaced that not every requirement is truly binary — some ("supports Jira bi-directional?") have an obvious yes/no, but the real differentiator between two "yes" vendors is how much work it takes to stand up and run. The scorecard scores these as two separate axes rather than one blended number:

- **Capability (primary, all requirements)** — the 0–3 Native/Config/Add-on/Custom-build/Not-supported score above. This is what feeds the weighted total. It's sourced from the RFI response and is comparable across every vendor and every requirement.
- **Effort — ease of use / setup time (secondary, POC-only)** — measured directly during the POC, not self-reported on the RFI. Concrete, not a rating: time to deploy (Flow 3: sidebar app in under 4 hours), click-count (Flow 4: Jira issue in under 3 clicks), extraction time (Flow 6: time to pull 20 tickets). Self-reported "ease of use" isn't used because it isn't verifiable or comparable across vendors — it's marketing-shaped, not evidence-shaped.

**These do not get averaged together.** Capability is the score that determines category and weighted totals. Effort is a tiebreaker: when two vendors score identically on Capability for a requirement, the POC's measured effort data decides which is preferred. Effort scores live in `vendor-poc-scope.md` alongside the gate/differentiator flows, not in the category tables below.
